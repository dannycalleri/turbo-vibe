# turbo-vibe

An open-source kit that deploys a project's services from one `turbo-vibe.yaml`. This repository holds the `turbo-vibe` CLI (published as `@turbo-vibe/cli`).

## Commands

- `make check` — the gate for every commit: `biome ci .`, `tsc --noEmit`, `vitest run`.
- `make build` — runs `npm run build`, which empties `dist/` and compiles `src/` into it with `tsc -p tsconfig.build.json` (one `.js` per source file, no bundler; the runtime dependencies are installed with the package). `dist/cli.js` keeps the `#!/usr/bin/env node` line of `src/cli.ts`.
- `make compatibility` — regenerates `COMPATIBILITY.md` (pinned versions per adapter, last live pass) through the hidden `turbo-vibe compatibility` command; a test fails when a pin changed and the file was not regenerated.
- `make schema` — regenerates `schema/turbo-vibe.schema.json` (shipped in the npm package) from the zod schema through the hidden `turbo-vibe schema` command; a test fails when the committed file is stale.
- `make integration` — `validate-infra`, `lint-workflows` (`actionlint`, local or the pinned Docker image), `integration-tests` (`test/integration/`, against real Postgres in Docker), and `dry-run-example` (a real `wrangler deploy --dry-run` of each example under `examples/` that deploys to Cloudflare, building their images with Docker). Not part of `make check`.
- `make validate-infra` — `tofu init -backend=false && tofu validate` on every module under `infra/`; uses a local `tofu` if present, otherwise the pinned OpenTofu Docker image.
- `npx vitest run test/<file>.test.ts` — one test file.
- `npx biome check --write .` — format and fix lint.

## Layout

- `src/cli.ts` — process entry; everything else is reachable through `main(argv, io)` in `src/main.ts`, which tests call directly.
- `src/config/` — the `turbo-vibe.yaml` schema (`zod`), the loader that turns schema issues into `line: message` problems, and `json-schema.ts`, which publishes the schema as JSON Schema with each kind's targets listed.
- `src/adapters/` — one adapter per target, all behind the contract in `types.ts`; `index.ts` is the registry the config validator reads.
- `src/infrastructure.ts` — composes adapter contributions into one OpenTofu root per project and environment, with state in R2.
- `src/apply.ts` — `turbo-vibe apply` and `plan --env`: writes the root to `.turbo-vibe/tofu/<env>/` and runs `tofu`; both save a plan, read it with `tofu show -json`, print the summary and delete the file; `apply` then applies that saved plan, and refuses one that deletes or replaces a resource outside a preview unless given `--allow-deletions` (the reusable workflows' `allow-deletions` input).
- `src/changes.ts` — turns OpenTofu's JSON plan into per-service creates, changes, replacements and deletions; a resource belongs to the service whose adapter contribution names it (Worker, route, hostname, Vercel project, `supabase_<service>`/`workos_<service>` module). Prints addresses and actions only.
- `src/deploy.ts` — `test`, `deploy`, and `smoke` across services; each adapter's `deploy` and `smoke` do the work. `deploy` hands backends runtime secrets (`DATABASE_URL` from OpenTofu outputs; `WORKOS_CLIENT_ID`, `WORKOS_API_KEY`, `WORKOS_REDIRECT_URI` from the environment) through `wrangler --secrets-file` and a `0600` file it deletes afterwards, and runs frontend builds with every kit credential removed from their environment.
- `src/adapters/wrangler.ts` — the generated Worker entry, its `health.js` (the Worker answers `/_turbo-vibe/health` by probing the container, and reports the build ID it was deployed with; the container gets that ID as `TURBO_VIBE_BUILD_ID`), its `routing.js` (which container instance a request reaches: `container.instance_from`, else `default`; with `instance_from`, the name ends in `@<build ID>`, so a deploy switches new requests to new instances at once instead of waiting for Cloudflare to replace a long-lived one), and `wrangler.json`, written to `.turbo-vibe/wrangler/<env>/<worker>/`. On a private environment with a frontend on another origin, the Worker also gets `guard.js` (it answers every `OPTIONS` request itself and refuses writes from other origins) and `sign-in.js` (`/_turbo-vibe/sign-in?return=`, which redirects only to the frontend's origins), and on any private environment `health.js` keeps the reason of a failure out of its public answer. `wrangler` and `@cloudflare/containers` are exact-pinned dependencies resolved from turbo-vibe's own `node_modules`.
- `src/migrate.ts`, `src/database.ts` — `turbo-vibe migrate`: reads the environment's OpenTofu outputs, checks the Supabase project is awake, creates the `turbo_vibe_migrator` and `turbo_vibe_runtime` roles as `postgres`, refuses when the database has a migration version the folder lacks (a rollback across a migration; `migrate --check` does only that, and `promote.yml` runs it before `apply`), then runs the pinned Supabase CLI's `db push` as the migrator over the session pooler.
- `src/adapters/vercel.ts` — `vercel-static` and `vercel-nextjs` (the latter runs `vercel build --prod` in `build.root` with a local `.vercel/project.json`, so no token is needed to build). `vercel-static`: Vercel project, domain and Cloudflare CNAME through OpenTofu; the CI build shipped as `.vercel/output` with the pinned Vercel CLI (`deploy --prebuilt --prod`), the project ID read from OpenTofu outputs. `src/adapters/assets.ts` holds the build, archive and restore steps both static adapters share.
- `src/origins.ts` — the hostname layout per environment: a frontend whose adapter is `crossOrigin` moves the backend to its API hostname. It computes the backend's exact allowed origins, the frontend's API URL, and the sign-in callback; it sets no cookie domain, so sign-in cookies stay host-only. Adapters get `hostname` (their own) and `backendHostname` in their context.
- `src/identity.ts` — before `apply`, lists the WorkOS environment's redirect URIs and decides which ones OpenTofu manages: only those the kit created or that do not exist yet.
- `src/builds.ts` — build records and asset archives in R2 (S3 API, signed with `aws4fetch`), and `choosePromotion`. `buildsBucket` picks the bucket: staging's own state bucket, or `TURBO_VIBE_BUILDS_BUCKET` (staging's bucket, read-only) in production. Staging `deploy` writes a record, staging `smoke` marks it, `promote` deploys a record's outputs only. Adapters' `deploy` returns `{ code, outputs }` and, given `recorded`, must not build.
- `src/ship.ts` — `turbo-vibe ship`: with the person's signed-in `gh`, lists the builds that passed staging (`src/staging-builds.ts`), lets them choose one (newest by default, a rollback named as such), and starts the production workflow with `gh workflow run … -f confirm-build=<sha>`, then prints the run's URL. It never deploys itself; without a terminal it needs `--build-id`.
- `src/staging-builds.ts` — the builds that passed staging, as GitHub's `staging` deployments list them (one `gh api graphql` call), and the summary `promote --describe` prints before an approval. The build records in R2 stay the authority: `promote --confirm <id>` accepts any build that passed (an older one is a rollback), and `--newest` keeps the newest-only rule for an approval from a Staging run.
- `src/assistant.ts` — the coding-assistant guidance, one text in two front-matter wrappers (Claude Code skill, Cursor rule), stamped with the CLI's version: `init --assistant` writes the guidance for working on a turbo-vibe project (the option takes a list such as `claude,cursor`, defaults to the assistants the repository already uses, and `--no-assistant` skips it; `both` and `none` remain as aliases); `adopt` writes `turbo-vibe-adopt`, which takes an agent from an existing repository to a pull request (inspect, map to targets, meet the backend contract, `init` with flags, check locally, hand over). Its target table is generated from the adapter registry, and its contract values come from `src/contract.ts` (default port, `/api/` prefix, `TURBO_VIBE_BUILD_ID`), which the adapters read too. `src/version.ts` `references()` names the CLI and workflow versions guidance and `init` write: the major line for a release, the exact version for a prerelease, which `@1` and `v1` never reach.
- `src/init.ts` — `turbo-vibe init`: answers to `turbo-vibe.yaml` (hostnames kept one level below the zone) and the two caller workflows; refuses to overwrite without `--force`; adds `.turbo-vibe/` to `.gitignore`; in a terminal with a signed-in `gh`, offers to run `setup`, then prints numbered next steps for what remains (`setup` first, with the reason, when it did not run). In a terminal it asks through `io.prompts` (`src/prompts.ts`, `@clack/prompts`: arrow-key choices, re-asked invalid answers, Ctrl-C exits 130 with nothing written), with defaults from `src/detect.ts` (name, and each target from a `Dockerfile`, a `next` dependency, a `build` script, a `supabase/` folder or a WorkOS SDK). Tests fake the prompts with `fakePrompts` in `test/harness.ts`.
- `src/preview.ts` — `turbo-vibe preview deploy|remove`: environments `preview-<branch slug>` (one-level hostnames next to staging's, own state key, Supabase branch of the main project, no build record). Removal runs each adapter's `remove`, then `destroy` (in `apply.ts`, which refuses non-preview environments).
- `src/setup.ts`, `src/setup/` — `turbo-vibe setup`: creates the GitHub environments (`preview` too when the config enables previews; `staging` and `production` limited to `main` by deployment-branch rules; a required reviewer on production), lists each environment's secret names, guides each vendor with a step from the table in `setup/steps.ts` (plan, dashboard clicks, permissions, an offer to open the page; Cloudflare's is a prefilled token template), gets values from `setup/cloudflare.ts` (account read from the bootstrap token; zone, state bucket, per-environment CI and R2 tokens, all from one bootstrap token through a one-hour setup token; waits for Workers Paid and R2) and `setup/vendors.ts` (Supabase organization and Vercel team found from their tokens), checks each pasted value at once under a spinner (`setup/checked.ts`) and asks again on failure; Ctrl-C at a choice throws `Cancelled`, which `setup` turns into exit 130; `setup/list.ts` is `setup --list`, the person's steps from the config alone, with no I/O; asks for the rest with `io.askSecret` (WorkOS keys checked per environment), and stores each value with `gh secret set` on stdin (`io.capture`'s `input`). It keeps secrets already present (`--replace` asks again; when every Cloudflare secret is kept it offers to add missing permissions to the existing CI tokens in place, from a bootstrap token), then runs `checksFor` with the values entered; findings carry `unset` names so kept secrets are not reported. The secret list is `environmentSecrets()` in `src/deploy.ts`, shared with the GitHub check; the CI token's permissions are `requiredPermissions()` from `src/checks/cloudflare.ts`.
- `src/check.ts`, `src/checks/` — `turbo-vibe check`: one function per vendor or concern returns findings (`ok`, `warn`, `fail` with a fix); `checksFor` picks the ones the project's targets need. Checks only read, apart from the state bucket's lock probe, which writes and deletes one object.
- `src/smoke.ts` — the build-ID check every adapter's smoke uses: about a minute of retries, five for a container backend while its Worker answers 503: a new container application's first start, or a container whose health route still reports the previous build (the switch-over after a deploy). An app error answers 502 and gets the usual minute.
- `src/adapters/rollout.ts` — after `wrangler deploy`, follows the rollout it started (the one absent from a snapshot taken before deploying; the application's own `version` lags) through Cloudflare's API until every instance runs the new image (17-minute limit, stops at once on `replaced` or `reverted`); `wrangler deploy` returns as soon as the rollout starts. In a dry run, the container adapter instead starts the image on its port (`container.port`, else the Dockerfile's `EXPOSE`, else 8080; `src/port.ts`), published on a random local port, and fails unless it answers the health probe that `smoke` will check (`/` below HTTP 500, or HTTP 2xx from `container.health`) and `docker stop` stops it without killing it, because a container that ignores `SIGTERM` holds every rollout for 15 minutes.
- `.github/workflows/deploy.yml` — the reusable workflow projects call; its `TURBO_VIBE_CLI` pin must equal `package.json`'s version (a test enforces it). The reusable workflows install that version with `npm pack`, unpack it, and run `npm ci --omit=dev --ignore-scripts` inside it, so `npm-shrinkwrap.json` is followed exactly; secrets sit in the `env` of the steps that call the CLI and nowhere else, so no install script ever sees them (a test enforces it). `promote.yml` is the reusable "Deploy to production": a `describe` job with no secret writes the build to promote to the summary before the approval (`promote --describe`), then the `production` job checks the reviewer rule, chooses (an empty `confirm-build` means the newest build only where `production` has a required reviewer), checks out that build's commit, applies, migrates, promotes by build ID and smokes; no build, called by the kit's `production.yml`. `preview.yml` is the reusable per-pull-request preview (deploy on open or sync, remove on close, a URL comment, a notice with no secrets for a fork or a run Dependabot starts, which gets only Dependabot's secrets), called by the kit's `previews.yml` for the database-less examples. `live-tests.yml` (the live tests) runs weekly (and on demand) from `main` through the reusable `live-run.yml`, in the `live` environment (GitHub holds as possibly malicious a workflow with its own trigger that passes `toJSON(secrets)`, so only `workflow_call` files do; a test enforces it): each example with `previews: true` is deployed as the preview of branch `live run <n>` (a name git forbids; any other branch that normalises to `live-run-…` gets a `pr-` prefix, so no pull request shares it), smoke-tested and removed; the Go example is dated by its latest passing staging build; then `turbo-vibe compatibility --results` updates `COMPATIBILITY.md`, proposed only when it changed, in a pull request from `live-results/<n>` opened with the `live` environment's `LIVE_RESULTS_TOKEN` (one opened with `GITHUB_TOKEN` runs no checks) and set to merge itself once `main`'s required checks pass; an older one still open is closed. `pipeline.yml` is the kit's own pipeline: its gate, then the example through `deploy.yml`, which deploys only after the gate passes.
- `docs/bootstrap.md` — the one-time accounts, plans and tokens a person creates before `setup`; keep it in step with what `setup` asks for, what `check` verifies, and what adapters declare as `secrets`.
- `docs/reference.md` — the README's details: each command, promotion, previews, the backend contract, each target, credentials and the three kinds of application values. The README stays short and links here; keep both in step with the code.
- `docs/adoption.md` — the adoption guide for an existing project; keep its config and workflow snippets in step with the schema and the reusable workflows.
- `.github/workflows/release.yml` — on each push to `main`, [release-please](https://github.com/googleapis/release-please) (`release-please-config.json`, `.release-please-manifest.json`) keeps a release pull request open, with the token in the repository secret `RELEASE_PLEASE_TOKEN` (`GITHUB_TOKEN` may not change workflow files): the next version from the Conventional Commits, `CHANGELOG.md`, `package.json`, `npm-shrinkwrap.json`, and the `TURBO_VIBE_CLI` pins of the three reusable workflows (lines marked `x-release-please-version`). Merging it tags `vX.Y.Z`; the same run then publishes in the protected `release` environment, only for a commit on `main`, after checking that the tag, the package, the shrinkwrap and the three pins agree and running the gate: `@turbo-vibe/cli` with provenance (npm trusted publishing), a prerelease (a version such as `1.1.0-rc.1`, chosen with a `Release-As` footer) under the dist-tag `next`. For a release that is not a prerelease it moves the `vX` tag, but only when it is the newest release (prereleases ignored) in its major line, so a patch to an older line never rolls adopters back. If `v*` tags are ever protected by a ruleset, allow GitHub Actions to bypass it, or the move is rejected. Pull requests are merged with "Rebase and merge", the only method the repository allows: release-please reads every commit on `main`, and a merge commit always carries the PR title, which it would list next to the PR's own commits. A stack is merged from the pull request of its top branch, so each slice's commit lands once and gets its own changelog line. To release, merge the release pull request. The first release is `initial-version` (`1.0.0-rc.1`). If publishing fails after the tag exists, re-run the failed jobs of that run. To choose a version, merge a commit whose message has a `Release-As: X.Y.Z` footer. Release candidates ended with `1.0.0`.
- `examples/go-api/` — the example the kit deploys: a Go API and a static page served from one Worker, with a Supabase database; `/api/health` reports the build ID and the row its migration (`supabase/migrations/`) inserts. `test/integration/migrate.test.ts` runs that migration. With `ALLOWED_ORIGINS` set it refuses other origins (`cors.go`). `examples/vercel-static/` deploys a page to Vercel against the same API on Cloudflare. `examples/python-api/` is a standard-library Python API on the same adapter as the Go one, routing by `?session=`; `examples/nextjs/` is a Next.js app with one server-rendered page; `test/integration/nextjs.test.ts` builds it with the real `vercel build`. `examples/go-api` signs users in with AuthKit (`auth.go`: `/api/auth/login`, `/api/auth/callback`, `/api/me`), tested by `auth_test.go` against a fake WorkOS token endpoint through the example's `build.test`.
- `infra/` — OpenTofu modules (`cloudflare`, `supabase`, `vercel`, `workos`), shipped in the npm package; the generated root calls one `supabase_<service>` module per database. OpenTofu owns long-lived resources (Worker entity, routes, DNS); `wrangler` ships Worker code. The only code a module uploads is a placeholder version when it creates a Worker, because Cloudflare refuses a route to a Worker with no code; `ignore_changes` keeps it from ever replacing wrangler's.
- `src/plan.ts` — derives what each environment runs from a validated config.
- `test/` — `vitest` unit tests, one file per module (`make check`); `test/harness.ts` holds the CLI runner and the fake R2 bucket, Docker, and runner used by `cli.test.ts` and `release.test.ts`; `test/integration/` needs Docker and runs under `make integration`.

## Conventions

- TypeScript strict on Node 24, ESM, `.js` suffixes in relative imports. `package.json` pins Node 24.12.0 for Volta and `packageManager` to that Node's npm; change dependencies with that npm, because another npm version writes the lockfile differently.
- npm is the only package manager: `npm-shrinkwrap.json` is the only lockfile, used by `npm install`/`npm ci` here and shipped in the package, so adopters install the tree the tests ran on (dev entries are skipped). Dependabot updates it directly. A test fails when it no longer matches `package.json`, or when another lockfile appears. `.npmrc` sets `save-exact` (direct dependencies pinned to exact versions) and `ignore-scripts` (no dependency's install script runs); Biome's `noUndeclaredDependencies` stops imports of packages that npm's flat `node_modules` would otherwise allow.
- Nothing external (network, child processes) runs before the config validates. Child processes go through `io.run` (output streamed) or `io.capture` (stdout returned); Postgres goes through `io.sql`. Tests fake them.
- Never print secret values; print names.
- Tests fake the outside world through `Io` (`src/io.ts`): `run`, `capture`, `fetch`, `sleep`, `sql`.
- Workflow actions are pinned by commit SHA with the tag in a comment.
- Commits follow Conventional Commits: `feat(config): …`, `fix(plan): …`, `chore: …`.
- Comments only where the code cannot carry the reason.
