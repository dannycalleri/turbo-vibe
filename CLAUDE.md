# turbo-vibe

An open-source kit that deploys a project's services from one `turbo-vibe.yaml`. This repository holds the `turbo-vibe` CLI (published as `@turbo-vibe/cli`).

## Commands

- `make check` — the gate for every commit: `biome ci .`, `tsc --noEmit`, `vitest run`.
- `make build` — runs `pnpm build`, which empties `dist/` and compiles `src/` into it with `tsc -p tsconfig.build.json` (one `.js` per source file, no bundler; the runtime dependencies are installed with the package). `dist/cli.js` keeps the `#!/usr/bin/env node` line of `src/cli.ts`.
- `make compatibility` — regenerates `COMPATIBILITY.md` (pinned versions per adapter, last live pass) through the hidden `turbo-vibe compatibility` command; a test fails when a pin changed and the file was not regenerated.
- `make shrinkwrap` — regenerates `npm-shrinkwrap.json`, the published package's pinned dependency tree; a test fails when it no longer matches `package.json` or pins a version `pnpm-lock.yaml` lacks (then update pnpm's lock, or add an npm `overrides` entry, and rerun it).
- `make schema` — regenerates `schema/turbo-vibe.schema.json` (shipped in the npm package) from the zod schema through the hidden `turbo-vibe schema` command; a test fails when the committed file is stale.
- `make integration` — `validate-infra`, `lint-workflows` (`actionlint`, local or the pinned Docker image), `integration-tests` (`test/integration/`, against real Postgres in Docker), and `dry-run-example` (a real `wrangler deploy --dry-run` of each example under `examples/` that deploys to Cloudflare, building their images with Docker). Not part of `make check`.
- `make validate-infra` — `tofu init -backend=false && tofu validate` on every module under `infra/`; uses a local `tofu` if present, otherwise the pinned OpenTofu Docker image.
- `pnpm exec vitest run test/<file>.test.ts` — one test file.
- `pnpm exec biome check --write .` — format and fix lint.

## Layout

- `src/cli.ts` — process entry; everything else is reachable through `main(argv, io)` in `src/main.ts`, which tests call directly.
- `src/config/` — the `turbo-vibe.yaml` schema (`zod`), the loader that turns schema issues into `line: message` problems, and `json-schema.ts`, which publishes the schema as JSON Schema with each kind's targets listed.
- `src/adapters/` — one adapter per target, all behind the contract in `types.ts`; `index.ts` is the registry the config validator reads.
- `src/infrastructure.ts` — composes adapter contributions into one OpenTofu root per project and environment, with state in R2.
- `src/apply.ts` — `turbo-vibe apply` and `plan --env`: writes the root to `.turbo-vibe/tofu/<env>/` and runs `tofu`; both save a plan, read it with `tofu show -json`, print the summary and delete the file; `apply` then applies that saved plan, and refuses one that deletes or replaces a resource outside a preview unless given `--allow-deletions` (the reusable workflows' `allow-deletions` input).
- `src/changes.ts` — turns OpenTofu's JSON plan into per-service creates, changes, replacements and deletions; a resource belongs to the service whose adapter contribution names it (Worker, route, hostname, Vercel project, `supabase_<service>`/`workos_<service>` module). Prints addresses and actions only.
- `src/deploy.ts` — `test`, `deploy`, and `smoke` across services; each adapter's `deploy` and `smoke` do the work. `deploy` hands backends runtime secrets (`DATABASE_URL` from OpenTofu outputs; `WORKOS_CLIENT_ID`, `WORKOS_API_KEY`, `WORKOS_REDIRECT_URI` from the environment) through `wrangler --secrets-file` and a `0600` file it deletes afterwards, and runs frontend builds with every kit credential removed from their environment.
- `src/adapters/wrangler.ts` — the generated Worker entry, its `routing.js` (which container instance a request reaches: `container.instance_from`, else `default`), and `wrangler.json`, written to `.turbo-vibe/wrangler/<env>/<worker>/`. `wrangler` and `@cloudflare/containers` are exact-pinned dependencies resolved from turbo-vibe's own `node_modules`.
- `src/migrate.ts`, `src/database.ts` — `turbo-vibe migrate`: reads the environment's OpenTofu outputs, checks the Supabase project is awake, creates the `turbo_vibe_migrator` and `turbo_vibe_runtime` roles as `postgres`, then runs the pinned Supabase CLI's `db push` as the migrator over the session pooler.
- `src/adapters/vercel.ts` — `vercel-static` and `vercel-nextjs` (the latter runs `vercel build --prod` in `build.root` with a local `.vercel/project.json`, so no token is needed to build). `vercel-static`: Vercel project, domain and Cloudflare CNAME through OpenTofu; the CI build shipped as `.vercel/output` with the pinned Vercel CLI (`deploy --prebuilt --prod`), the project ID read from OpenTofu outputs. `src/adapters/assets.ts` holds the build, archive and restore steps both static adapters share.
- `src/origins.ts` — the hostname layout per environment: a frontend whose adapter is `crossOrigin` moves the backend to its API hostname. It computes the backend's exact allowed origins, the frontend's API URL, and the sign-in callback; it sets no cookie domain, so sign-in cookies stay host-only. Adapters get `hostname` (their own) and `backendHostname` in their context.
- `src/identity.ts` — before `apply`, lists the WorkOS environment's redirect URIs and decides which ones OpenTofu manages: only those the kit created or that do not exist yet.
- `src/builds.ts` — build records and asset archives in R2 (S3 API, signed with `aws4fetch`), and `choosePromotion`. `buildsBucket` picks the bucket: staging's own state bucket, or `TURBO_VIBE_BUILDS_BUCKET` (staging's bucket, read-only) in production. Staging `deploy` writes a record, staging `smoke` marks it, `promote` deploys a record's outputs only. Adapters' `deploy` returns `{ code, outputs }` and, given `recorded`, must not build.
- `src/assistant.ts` — the coding-assistant guidance `init --assistant` writes (Claude Code skill, Cursor rule), one text in two front-matter wrappers, stamped with the CLI's version.
- `src/init.ts` — `turbo-vibe init`: answers to `turbo-vibe.yaml` (hostnames kept one level below the zone) and the two caller workflows; refuses to overwrite without `--force`. Interactive questions go through the optional `io.ask`.
- `src/preview.ts` — `turbo-vibe preview deploy|remove`: environments `preview-<branch slug>` (one-level hostnames next to staging's, own state key, Supabase branch of the main project, no build record). Removal runs each adapter's `remove`, then `destroy` (in `apply.ts`, which refuses non-preview environments).
- `src/setup.ts`, `src/setup/` — `turbo-vibe setup`: creates the GitHub environments (`preview` too when the config enables previews; `staging` and `production` limited to `main` by deployment-branch rules; a required reviewer on production), lists each environment's secret names, gets values from `setup/cloudflare.ts` (zone, state bucket, per-environment CI and R2 tokens, all from one bootstrap token through a one-hour setup token; waits for Workers Paid and R2) and `setup/vendors.ts` (Supabase organization and Vercel team found from their tokens); `setup/list.ts` is `setup --list`, the person's steps from the config alone, with no I/O; asks for the rest with `io.askSecret` (WorkOS keys checked per environment), and stores each value with `gh secret set` on stdin (`io.capture`'s `input`). It keeps secrets already present (`--replace` asks again), then runs `checksFor` with the values entered; findings carry `unset` names so kept secrets are not reported. The secret list is `environmentSecrets()` in `src/deploy.ts`, shared with the GitHub check; the CI token's permissions are `requiredPermissions()` from `src/checks/cloudflare.ts`.
- `src/check.ts`, `src/checks/` — `turbo-vibe check`: one function per vendor or concern returns findings (`ok`, `warn`, `fail` with a fix); `checksFor` picks the ones the project's targets need. Checks only read, apart from the state bucket's lock probe, which writes and deletes one object.
- `src/smoke.ts` — the build-ID check every adapter's smoke uses.
- `src/adapters/rollout.ts` — after `wrangler deploy`, follows the rollout it started (the one absent from a snapshot taken before deploying; the application's own `version` lags) through Cloudflare's API until every instance runs the new image (17-minute limit, stops at once on `replaced` or `reverted`); `wrangler deploy` returns as soon as the rollout starts. In a dry run, the container adapter instead starts the image and fails if `docker stop` has to kill it, because a container that ignores `SIGTERM` holds every rollout for 15 minutes.
- `.github/workflows/deploy.yml` — the reusable workflow projects call; its `TURBO_VIBE_CLI` pin must equal `package.json`'s version (a test enforces it). `promote.yml` is the reusable "Deploy to production" (choose, check out that build's commit, apply, migrate, promote by build ID, smoke; no build), called by the kit's `production.yml`. `preview.yml` is the reusable per-pull-request preview (deploy on open or sync, remove on close, a URL comment, a fork notice with no secrets), called by the kit's `previews.yml` for the database-less examples. `live-tests.yml` (the live tests) runs weekly (and on demand) from `main` in the `live` environment: each example with `previews: true` is deployed as the preview of branch `live run <n>` (a name git forbids; any other branch that normalises to `live-run-…` gets a `pr-` prefix, so no pull request shares it), smoke-tested and removed; the Go example is dated by its latest passing staging build; then `turbo-vibe compatibility --results` updates `COMPATIBILITY.md`, committed only when it changed. `pipeline.yml` is the kit's own pipeline: its gate, then the example through `deploy.yml`, which deploys only after the gate passes.
- `docs/bootstrap.md` — the one-time accounts, plans and tokens a person creates before `setup`; keep it in step with what `setup` asks for, what `check` verifies, and what adapters declare as `secrets`.
- `docs/adoption.md` — the adoption guide for an existing project; keep its config and workflow snippets in step with the schema and the reusable workflows.
- `.github/workflows/release.yml` — on a `vX.Y.Z` tag: checks that the tag, `package.json` and the CLI pins of all three reusable workflows (deploy, promote, preview) agree, runs the gate, publishes `@turbo-vibe/cli` with provenance (npm trusted publishing), then moves the `vX` tag, but only when the release is the newest in its major line, so a patch to an older line never rolls adopters back. If `v*` tags are ever protected by a ruleset, allow GitHub Actions to bypass it, or the move is rejected. To release, bump `package.json` and the three `TURBO_VIBE_CLI` pins together, run `make schema compatibility shrinkwrap`, merge, and push the tag.
- `examples/go-api/` — the example the kit deploys: a Go API and a static page served from one Worker, with a Supabase database; `/api/health` reports the build ID and the row its migration (`supabase/migrations/`) inserts. `test/integration/migrate.test.ts` runs that migration. With `ALLOWED_ORIGINS` set it refuses other origins (`cors.go`). `examples/vercel-static/` deploys a page to Vercel against the same API on Cloudflare. `examples/python-api/` is a standard-library Python API on the same adapter as the Go one, routing by `?session=`; `examples/nextjs/` is a Next.js app with one server-rendered page; `test/integration/nextjs.test.ts` builds it with the real `vercel build`. `examples/go-api` signs users in with AuthKit (`auth.go`: `/api/auth/login`, `/api/auth/callback`, `/api/me`), tested by `auth_test.go` against a fake WorkOS token endpoint through the example's `build.test`.
- `infra/` — OpenTofu modules (`cloudflare`, `supabase`, `vercel`, `workos`), shipped in the npm package; the generated root calls one `supabase_<service>` module per database. OpenTofu owns long-lived resources (Worker entity, routes, DNS); `wrangler` ships Worker code. The only code a module uploads is a placeholder version when it creates a Worker, because Cloudflare refuses a route to a Worker with no code; `ignore_changes` keeps it from ever replacing wrangler's.
- `src/plan.ts` — derives what each environment runs from a validated config.
- `test/` — `vitest` unit tests, one file per module (`make check`); `test/harness.ts` holds the CLI runner and the fake R2 bucket, Docker, and runner used by `cli.test.ts` and `release.test.ts`; `test/integration/` needs Docker and runs under `make integration`.

## Conventions

- TypeScript strict on Node 24, ESM, `.js` suffixes in relative imports.
- Direct dependencies are pinned to exact versions (`.npmrc` sets `save-exact`); commit `pnpm-lock.yaml`.
- Nothing external (network, child processes) runs before the config validates. Child processes go through `io.run` (output streamed) or `io.capture` (stdout returned); Postgres goes through `io.sql`. Tests fake them.
- Never print secret values; print names.
- Tests fake the outside world through `Io` (`src/io.ts`): `run`, `capture`, `fetch`, `sleep`, `sql`.
- Workflow actions are pinned by commit SHA with the tag in a comment.
- Commits follow Conventional Commits: `feat(config): …`, `fix(plan): …`, `chore: …`.
- Comments only where the code cannot carry the reason.
